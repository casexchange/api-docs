This guide is for pharmacies that connect a pharmacy management system to **Med Xchange (MedEx)**. A law firm refers its client to your pharmacy. You record what you dispensed and billed, every payment, adjustment and refund against it, and the balance your own system shows. The firm sees the totals and the detail in MedEx, beside the rest of its client's medical care.

Everything here sits on **your pharmacy's referral**, not on an appointment. You don't create appointments or billing lines to record a fill.

Read [MedEx for medical providers](/api-reference/examples/medex-providers) first. It covers provider keys, the referral lifecycle and webhook delivery, which this guide builds on.

**Base URL:** `https://api.casexchange.com/api/public/v1` in production. Build and test against UAT first: see [Test in UAT](#test-in-uat).

**Authentication:** pass your key in the `X-API-Key` header on every request. Responses use the standard envelope described in [Response Format](/api-reference/response-format).

Field-by-field request and response schemas live in the API tab under **Endpoints → MedEx Pharmacy**. This page explains how those endpoints fit together.

## Before you start

### Your key

| Tier | Key prefix | Pharmacy ledger |
|---|---|---|
| `read_only` | `cxpp_ro_...` | Read fills, transactions, the balance and balance snapshots, and list routed prescriptions |
| `standard` | `cxpp_std_...` | Everything above, plus record and correct fills, transactions and balance snapshots, and upload documents |
| `full` | `cxpp_full_...` | The same as `standard` for a pharmacy |

A `read_only` key that tries a write gets `403 insufficient_tier`. The law firm on the case can read your ledger, but can't change it.

### Your practice must be set up as a pharmacy

CaseXchange marks a practice as a pharmacy. If yours isn't marked, ledger writes on your referral return `403 pharmacy_only`, and so does `GET /med-cases/{caseId}/prescriptions`. Ledger reads still work and come back empty. If you get `pharmacy_only`, ask [help@casexchange.com](mailto:help@casexchange.com) to check your setup.

A restricted-access practice gets `403 restricted_access` on every ledger endpoint.

### When you can write

You write to the ledger of **your own referral** on a case. The referral's status decides whether new records are accepted:

| Referral status | New fills, transactions and snapshots |
|---|---|
| `sent`, `under_review` | Refused with `409 referral_not_writable`. Accept the referral first |
| `rejected` | Refused with `409 referral_not_writable` |
| `accepted`, `in_treatment`, `treatment_complete` | Allowed |
| `closed`, `withdrawn` | Allowed. Payments often arrive after a case settles and the firm closes the referral |
| Any status, if the referral is archived | Refused with `409 referral_not_writable` |

Reads work in every status. Changes to existing fills and transactions follow the same rule.

A pharmacy referral normally goes `sent` → `under_review` → `accepted` and stays `accepted` until the firm closes it. `start-treatment` and `complete-treatment` don't apply to pharmacies (see [Pharmacies](/api-reference/examples/medex-providers#pharmacies)). `accept` also acknowledges a `sent` referral, so a single call opens the ledger.

Resending a record you've already created succeeds in any status. See [Idempotency](#idempotency).

### Test in UAT

Build against UAT, the environment for testing integrations. It runs the same API against synthetic firms and patients, so you can acknowledge, accept and reject referrals and write to the ledger without touching a real case.

| Environment | Base URL |
|---|---|
| UAT | `https://api-uat.casexchange.com/api/public/v1` |
| Production | `https://api.casexchange.com/api/public/v1` |

UAT and production keys are separate. A production key doesn't work in UAT, and a UAT key doesn't work in production. To get a UAT key and test referrals, email [help@casexchange.com](mailto:help@casexchange.com). See [Base URLs](/api-reference/overview#base-urls).

    ```json
      "pagination": { "page": 1, "limit": 100, "total": 1, "totalPages": 1 },

    ```

  </Step>

  <Step title="Find your referral and check its status">
    `GET /med-cases/{id}/referrals` lists **your pharmacy's** referrals on the case. Note the referral `id`, which every ledger call needs, and check its `status` against [When you can write](#when-you-can-write).

    ```bash
    curl "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals" \
      -H "X-API-Key: cxpp_ro_your_key_here"
    ```

    The ledger lives under that referral:

    ```
    /med-cases/{caseId}/referrals/{referralId}/pharmacy/fills
    /med-cases/{caseId}/referrals/{referralId}/pharmacy/transactions

    ```

    Another practice's referral returns `404`.
  </Step>

  <Step title="Find the prescription routed to you">
    When the treating practice routes a prescription to your pharmacy, `GET /med-cases/{caseId}/prescriptions` lists it. Use its `id` as `prescriptionId` when you record the fill.

    ```bash
    curl "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/prescriptions" \
      -H "X-API-Key: cxpp_ro_your_key_here"
    ```

    ```json
    {
      "data": [
        {
          "id": "3f6b9d2a-8c41-4e75-b1a0-c95e7d2f4a68",
          "drugName": "Cyclobenzaprine 10 mg tablet",

          "numRefills": 1,
          "lastRefillDate": null,
          "datePrescribed": "2026-10-01",
          "prescriber": { "id": "7a2d5f8c-1e94-4b36-a8c7-0d3f6b9e2c51", "name": "Testclinic Orthopedics" },
          "appointmentDate": "2026-10-01"
        }
      ],
      "meta": { "requestId": "req_5f6a7b8c9d0e1f2a3b4c5d6e", "timestamp": "2026-10-02T13:00:05.000Z" }
    ```

    - The list holds only prescriptions routed to **your** pharmacy. `prescriber` is the practice that wrote the prescription. The list isn't paginated.

    After the firm closes or withdraws your referral, this list is empty, but you can still record fills and payments. When you first match a fill to a prescription, save the `prescriptionId` in your own system.

  </Step>

Webhooks tell you about new work as it happens: `referral.sent` when a firm sends you a referral, and `prescription.created` when a prescription is routed to you. See [Webhooks](#webhooks).

## Fills

A fill is one dispensing of a prescription: what you dispensed, when, and what you billed for it. Fills are corrected or voided, never deleted.

### Record a fill

```bash
curl -X POST "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals/9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75/pharmacy/fills" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "externalId": "prx-fill-100245-1",
    "rxNumber": "RX-100245",
    "fillDate": "2026-10-02",
    "ndc": "12345-6789-01",
    "drugName": "Cyclobenzaprine 10 mg tablet",
    "quantity": "30",
    "daysSupply": 30,
    "prescriberName": "Dr. Testdoctor Bravo",
    "billedAmount": "120.00",
    "prescriptionId": "3f6b9d2a-8c41-4e75-b1a0-c95e7d2f4a68"
  }'
```

**Response `201 Created`:**

```json
{
  "data": {
    "id": "4b8e1d6a-9f23-4c57-8e0b-2a6d9c1f7e34",
    "medCaseId": "5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10",
    "medReferralId": "9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75",
    "externalId": "prx-fill-100245-1",
    "rxNumber": "RX-100245",
    "fillDate": "2026-10-02",
    "ndc": "12345678901",
    "drugName": "Cyclobenzaprine 10 mg tablet",
    "quantity": "30.000",
    "daysSupply": 30,
    "prescriberName": "Dr. Testdoctor Bravo",
    "billedAmount": "120.00",
    "prescriptionId": "3f6b9d2a-8c41-4e75-b1a0-c95e7d2f4a68",
    "claimDocumentId": null,
    "notes": null,
    "voidedAt": null,
    "voidReason": null,
    "createdVia": "api",
    "createdAt": "2026-10-02T14:10:00.000Z",
    "updatedAt": "2026-10-02T14:10:00.000Z"
  },
  "meta": { "requestId": "req_6a7b8c9d0e1f2a3b4c5d6e7f", "timestamp": "2026-10-02T14:10:00.000Z" }
}
```

| Field | Required | Format |
|---|---|---|
| `externalId` | Strongly recommended | Your own ID for this fill, 1–200 characters. See [Idempotency](#idempotency) |
| `rxNumber` | Yes | 1–50 characters |
| `fillDate` | Yes | `YYYY-MM-DD` |
| `drugName` | Yes | 1–500 characters |
| `billedAmount` | Yes | A non-negative decimal string with up to 2 decimal places, such as `"120.00"`. `"120"` is accepted and returned as `"120.00"` |
| `ndc` | No | 11 digits. Hyphens and spaces are removed. See [NDC format](#ndc-format) |
| `quantity` | No | A decimal string greater than 0, with up to 3 decimal places. It's returned with 3, so `"30"` comes back as `"30.000"` |
| `daysSupply` | No | A whole number from 0 to 3650, sent as a JSON number |
| `prescriberName` | No | Free text, up to 300 characters. The prescriber doesn't have to be on CaseXchange |
| `prescriptionId` | No | A prescription routed to you on this case, from `GET /med-cases/{caseId}/prescriptions` |
| `claimDocumentId` | No | A document on this case that you can see, usually the claim form you uploaded. See [Prescription and claim documents](#prescription-and-claim-documents) |
| `notes` | No | Up to 2,000 characters |

An unknown field, or a value in the wrong format, returns `400 validation_error` with each problem listed in `error.details.errors`. A `prescriptionId` that isn't routed to you on this case, or a `claimDocumentId` that isn't on this case or that you can't see, returns `400 invalid_reference`.

### NDC format

Send the 11-digit NDC in the 5-4-2 layout. CaseXchange removes hyphens and spaces, then requires exactly 11 digits, and returns the NDC without hyphens.

Removing hyphens does **not** pad a 10-digit NDC. NDCs printed on packages in the 4-4-2, 5-3-2 or 5-4-1 layout have 10 digits. Convert them to 5-4-2 by adding a leading zero to the short segment: `1234-5678-90` becomes `01234-5678-90`. A 10-digit NDC returns `400 validation_error` with the message `NDC must be 11 digits (hyphens allowed)`.

### Read fills

`GET .../pharmacy/fills` lists the referral's fills, newest `fillDate` first. It accepts:

- `fillDateFrom` and `fillDateTo` (`YYYY-MM-DD`, inclusive)
- `externalId`, to find the fill you created with that ID
- `includeVoided` (`true` by default; pass `false` to hide voided fills)
- `page` and `limit` (up to 100, default 20)

`GET .../pharmacy/fills/{fillId}` returns one fill plus:

- `transactions`: the transactions linked to that fill, oldest first
- `totals`: the fill's own `billed`, `paid`, `adjustments` and `computedBalance`, in the same shape as [the balance](#balance). `reported` and `difference` are always `null` here. For a voided fill, `billed` is `"0.00"` and `fillCount` is `0`, but its transactions still count.

### Correct a fill

`PATCH .../pharmacy/fills/{fillId}` changes any of these fields: `rxNumber`, `fillDate`, `ndc`, `drugName`, `quantity`, `daysSupply`, `prescriberName`, `billedAmount`, `prescriptionId`, `claimDocumentId` and `notes`. Send at least one. Send `null` to clear an optional field.

```bash
curl -X PATCH "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals/9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75/pharmacy/fills/4b8e1d6a-9f23-4c57-8e0b-2a6d9c1f7e34" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "notes": "Prior authorization approved 2026-10-01" }'
```

It returns `200` with the updated fill. The change is recorded in the case history, and a change to `billedAmount` records both the old and new amounts.

- You can't change `externalId` or the void fields: sending them returns `400 validation_error`.
- A voided fill can't be changed: `409 fill_voided`.
- The referral must be in a status that [accepts writes](#when-you-can-write).

<Note>
After you PATCH a fill, sending its original `POST` again with the same `externalId` returns `409 external_id_conflict`, because the fill no longer matches that body. Once you have a fill's CaseXchange `id`, update it with `PATCH` rather than resending the `POST`. See [Idempotency](#idempotency).
</Note>

### Void a fill

Void a fill that was entered in error or reversed in your system:

```bash
curl -X POST "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals/9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75/pharmacy/fills/6e3a9c2f-5d18-4b74-a9e6-0c4f8b2d1a57/void" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "reason": "Entered in error: duplicate of RX-100245" }'
```

`reason` is required (1–1,000 characters). The response is `200` with the fill, with `voidedAt` and `voidReason` set. A voided fill:

- no longer counts towards `billed` or `fillCount`;
- stays in the fills list and keeps its history, so the firm still sees it, marked as voided;
- can't be changed or voided again (`409 fill_voided`);
- **keeps its transactions, and they still count.** If money was posted against it, post [reversals](#reversals) to back that money out.

A void can't be undone. If the fill was real after all, record it again as a new fill with a new `externalId`.

## Transactions

Every payment, adjustment, write-off, refund and reversal is a transaction. The transaction ledger is **append-only**: a transaction's money never changes after it's recorded, and transactions are never deleted. To correct money, post a [reversal](#reversals).

| `type` | Use it for | Counts in |
|---|---|---|
| `PAYMENT` | Money received from a payer (positive), or taken back by a payer (negative) | `paid` |
| `REFUND` | Money you send back, such as returning an overpayment (usually negative) | `paid` |
| `ADJUSTMENT` | Contractual write-downs and other adjustments | `adjustments` |
| `WRITE_OFF` | A balance you write off | `adjustments` |
| `REVERSAL` | Undoing an earlier transaction | The same bucket as the transaction it reverses |

### The sign convention

A positive `amount` reduces the balance, and a negative `amount` increases it. The balance is `billed − paid − adjustments`.

| What happened | `type` | `amount` | Balance |
|---|---|---|---|
| A payer pays you 40.00 | `PAYMENT` | `"40.00"` | Down 40.00 |
| The payer takes the 40.00 back | `PAYMENT` with `"-40.00"`, or a `REVERSAL` of `"-40.00"` pointing at the payment | `"-40.00"` | Up 40.00 |
| A contractual write-down of 15.00 | `ADJUSTMENT` | `"15.00"` | Down 15.00 |
| You write off 5.00 | `WRITE_OFF` | `"5.00"` | Down 5.00 |
| You refund a 10.00 overpayment | `REFUND` | `"-10.00"` | Up 10.00 |
| You undo that 5.00 write-off | `REVERSAL` with `reversesTransactionId` set to the write-off | `"-5.00"` | Up 5.00 |

CaseXchange stores each amount exactly as you send it and doesn't check its sign against its type, because real ledgers contain unusual rows. Map your system's sign convention once in your integration, and test each type in UAT. An amount of zero is allowed.

### Record a transaction

```bash
curl -X POST "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals/9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75/pharmacy/transactions" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "externalId": "prx-txn-55001",
    "type": "PAYMENT",
    "amount": "80.00",
    "transactionDate": "2026-10-09",
    "fillId": "4b8e1d6a-9f23-4c57-8e0b-2a6d9c1f7e34",
    "payer": "Testpayer Mutual",
    "reference": "EFT-0001"
  }'
```

**Response `201 Created`:**

```json
{
  "data": {
    "id": "d2c4e6f8-1a3b-4c5d-8e7f-9a0b1c2d3e41",
    "medCaseId": "5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10",
    "medReferralId": "9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75",
    "externalId": "prx-txn-55001",
    "fillId": "4b8e1d6a-9f23-4c57-8e0b-2a6d9c1f7e34",
    "type": "PAYMENT",
    "amount": "80.00",
    "transactionDate": "2026-10-09",
    "payer": "Testpayer Mutual",
    "reference": "EFT-0001",
    "reversesTransactionId": null,
    "note": null,
    "createdVia": "api",
    "createdAt": "2026-10-09T16:00:00.000Z",
    "updatedAt": "2026-10-09T16:00:00.000Z"
  },
  "meta": { "requestId": "req_7b8c9d0e1f2a3b4c5d6e7f8a", "timestamp": "2026-10-09T16:00:00.000Z" }
}
```

| Field | Required | Format |
|---|---|---|
| `externalId` | Strongly recommended | Your own ID for this transaction, 1–200 characters. See [Idempotency](#idempotency) |
| `type` | Yes | `PAYMENT`, `ADJUSTMENT`, `WRITE_OFF`, `REFUND` or `REVERSAL` |
| `amount` | Yes | A decimal string, optionally negative, with up to 2 decimal places, such as `"-40.00"` |
| `transactionDate` | Yes | `YYYY-MM-DD` |
| `fillId` | No | A fill on this referral. Leave it out for money that isn't tied to one fill, such as a lump-sum payment |
| `payer` | No | Up to 300 characters |
| `reference` | No | A check or EFT number, up to 200 characters |
| `reversesTransactionId` | No | Only with `type: "REVERSAL"`: the transaction being reversed. With any other type it returns `400 validation_error` |
| `note` | No | Up to 2,000 characters |

Record the fill before any transaction that names it: a `fillId` or `reversesTransactionId` that isn't on this referral returns `400 invalid_reference`.

`GET .../pharmacy/transactions` lists the referral's transactions, newest `transactionDate` first. You can filter by `fillId`, `type`, `dateFrom`, `dateTo` (inclusive) and `externalId`, and page with `page` and `limit` (up to 100). `GET .../pharmacy/transactions/{transactionId}` returns one transaction.

### What you can change afterwards

`PATCH .../pharmacy/transactions/{transactionId}` changes only `payer`, `reference`, `note` and `fillId`. Use `fillId` to move a transaction to another fill, or send `null` to un-apply it.

```bash
curl -X PATCH "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals/9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75/pharmacy/transactions/d2c4e6f8-1a3b-4c5d-8e7f-9a0b1c2d3e41" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{ "reference": "EFT-0001-A" }'
```

`type`, `amount`, `transactionDate` and `reversesTransactionId` never change. A PATCH that names any of them, even with the value it already has, returns `400 immutable_field`, and `error.details.fields` lists the fields:

```json
{
  "error": {
    "code": "immutable_field",
    "message": "amount cannot be changed after a transaction is recorded; post a REVERSAL instead",
    "details": { "fields": ["amount"] }
  },
  "meta": { "requestId": "req_8c9d0e1f2a3b4c5d6e7f8a9b", "timestamp": "2026-10-10T09:00:00.000Z" }
}
```

### Reversals

A reversal undoes an earlier transaction on the same referral. Post a `REVERSAL` with `reversesTransactionId` set to that transaction, usually for the negative of its amount:

```json
{ "externalId": "prx-txn-55007", "type": "REVERSAL", "amount": "-20.00", "transactionDate": "2026-10-16", "reversesTransactionId": "d2c4e6f8-1a3b-4c5d-8e7f-9a0b1c2d3e46" }
```

- A reversal counts in the same bucket as the transaction it reverses. Reversing a `WRITE_OFF` changes `adjustments`, and reversing a `PAYMENT` changes `paid`.
- A **reversal of a reversal** follows the chain back to the original transaction and counts in that transaction's bucket. Use it when the reversal itself was the mistake.
- A `REVERSAL` with no `reversesTransactionId` counts in `paid`.
- CaseXchange doesn't check the reversal amount against the original, and doesn't stop you reversing the same transaction twice. Before you post one, list the referral's reversals (`?type=REVERSAL`) and check their `reversesTransactionId`.
- To correct an amount, reverse the original and record a new transaction with its own new `externalId`.

### Worked example

Fill `RX-100245` is billed at 120.00. A second fill, `RX-100246` for 45.00, was entered in error and voided, so it doesn't count. These eight transactions are then posted against `RX-100245`:

| # | What happened | `type` | `amount` | `paid` | `adjustments` | Balance |
|---|---|---|---|---|---|---|
| | Fill billed | | | 0.00 | 0.00 | 120.00 |
| T1 | Testpayer Mutual pays | `PAYMENT` | `"80.00"` | 80.00 | 0.00 | 40.00 |
| T2 | Contractual write-down | `ADJUSTMENT` | `"15.00"` | 80.00 | 15.00 | 25.00 |
| T3 | Testpayer Casualty pays, 10.00 too much | `PAYMENT` | `"35.00"` | 115.00 | 15.00 | -10.00 |
| T4 | You refund the overpayment | `REFUND` | `"-10.00"` | 105.00 | 15.00 | 0.00 |
| T5 | Testpayer Mutual takes 20.00 back on audit | `PAYMENT` | `"-20.00"` | 85.00 | 15.00 | 20.00 |
| T6 | You write off the 20.00 | `WRITE_OFF` | `"20.00"` | 85.00 | 35.00 | 0.00 |
| T7 | The write-off was a mistake: reverse T6 | `REVERSAL` → T6 | `"-20.00"` | 85.00 | 15.00 | 20.00 |
| T8 | The write-off was right after all: reverse T7 | `REVERSAL` → T7 | `"20.00"` | 85.00 | 35.00 | 0.00 |

A negative balance, as after T3, is a credit. T7 reverses a write-off, so it counts in `adjustments`. T8 is a reversal of a reversal: it follows T7 back to T6, a `WRITE_OFF`, so it also counts in `adjustments`.

## Balance

`GET .../pharmacy/balance` returns the referral's totals as CaseXchange computes them, next to the balance your system last reported. This is the referral from the worked example, after the snapshot of 2026-10-17 described below:

```json
{
  "data": {
    "billed": "120.00",
    "paid": "85.00",
    "adjustments": "35.00",
    "computedBalance": "0.00",
    "reported": {
      "balance": "0.00",
      "asOf": "2026-10-17T23:00:00.000Z",
      "externalId": "prx-bal-9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75-2026-10-17"
    },
    "difference": "0.00",
    "fillCount": 1,
    "transactionCount": 8
  },
  "meta": { "requestId": "req_9d0e1f2a3b4c5d6e7f8a9b0c", "timestamp": "2026-10-18T08:00:00.000Z" }
}
```

| Field | Meaning |
|---|---|
| `billed` | The total `billedAmount` of fills that aren't voided |
| `paid` | `PAYMENT` and `REFUND` amounts, plus reversals of them and reversals that name no transaction |
| `adjustments` | `ADJUSTMENT` and `WRITE_OFF` amounts, plus reversals of them |
| `computedBalance` | `billed − paid − adjustments`. Negative means a credit |
| `reported` | Your most recent balance snapshot (the latest `asOf`; on a tie, the one recorded last), or `null` if you haven't reported one |
| `difference` | `reported.balance − computedBalance`, or `null` with no snapshot |
| `fillCount` | Fills that aren't voided |
| `transactionCount` | Every transaction, reversals included |

The firm sees both balances in MedEx.

### Report your balance

Your system's balance is the figure the firm will usually ask about. Record it as a snapshot:

```bash
curl -X POST "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/referrals/9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75/pharmacy/balance-snapshots" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -H "Content-Type: application/json" \
  -d '{
    "externalId": "prx-bal-9c47b2e1-3f58-4a06-b8d2-6e1f0a9c3b75-2026-10-15",
    "balance": "20.00",
    "asOf": "2026-10-15T23:00:00Z"
  }'
```

| Field | Required | Format |
|---|---|---|
| `externalId` | Strongly recommended | Your own ID for this snapshot, 1–200 characters. Include the referral, as in the example. See [Idempotency](#idempotency) |
| `balance` | Yes | A decimal string, optionally negative, with up to 2 decimal places |
| `asOf` | Yes | When your system computed the balance: an ISO 8601 timestamp with `Z` or an offset, such as `2026-10-15T23:00:00Z` or `2026-10-15T19:00:00-04:00` |
| `note` | No | Up to 2,000 characters |

The response is `201` with the snapshot. Snapshots are append-only and can't be changed or deleted. `GET .../pharmacy/balance-snapshots` lists them, latest `asOf` first, with `page` and `limit`.

`difference` compares your latest snapshot with the ledger **as it is now**, not as it was at `asOf`. In the worked example:

- The snapshot above reports 20.00 as of 2026-10-15, which matches the ledger after T5.
- After T6, T7 and T8, the computed balance is 0.00, so `difference` is `"20.00"`, even though both systems agreed when the snapshot was taken.
- Reporting again (`"balance": "0.00"`, `"asOf": "2026-10-17T23:00:00Z"`, with a new `externalId`) brings `difference` back to `"0.00"`, as in the response above.

Report a new snapshot after each sync. A difference that remains after that means the two ledgers really disagree, which usually means a transaction one side has and the other doesn't. A positive `difference` means your system says more is owed than CaseXchange computes. List the referral's transactions and compare them with your records.

## Idempotency

Send an `externalId` on every create: fills, transactions, balance snapshots and document uploads. It's your own permanent ID for the record, and it makes every create safe to retry.

| You send | You get |
|---|---|
| An `externalId` you haven't used before | `201 Created` and the new record |
| The same `externalId` with the same content | `200 OK` and the **existing** record, with `"replayed": true` in `meta`. Nothing new is written, logged, emailed or sent as a webhook |
| The same `externalId` with different content | `409 external_id_conflict`, and `error.details.existingId` is the existing record's ID |
| No `externalId` | `201 Created` every time. A retry creates a duplicate |

A replay looks like this:

```json
{
  "data": { "id": "4b8e1d6a-9f23-4c57-8e0b-2a6d9c1f7e34", "externalId": "prx-fill-100245-1", "rxNumber": "RX-100245", "billedAmount": "120.00" },
  "meta": { "requestId": "req_0e1f2a3b4c5d6e7f8a9b0c1d", "timestamp": "2026-10-02T14:10:30.000Z", "replayed": true }
}
```

(The example is shortened; `data` is the full record.) A conflict looks like this:

```json
{
  "error": {
    "code": "external_id_conflict",
    "message": "externalId already exists with different content (the record may have been edited since it was created); PATCH details.existingId instead.",
    "details": { "existingId": "4b8e1d6a-9f23-4c57-8e0b-2a6d9c1f7e34" }
  },
  "meta": { "requestId": "req_1f2a3b4c5d6e7f8a9b0c1d2e", "timestamp": "2026-10-03T09:00:00.000Z" }
}
```

### The rules

- **Scope.** An `externalId` is unique across your whole pharmacy, separately for each kind of record. Your fill IDs are checked against your fills on every case and referral, your transaction IDs against your transactions, and so on. A fill and a transaction may share an ID, but two fills may not.
- **The referral is part of the content.** Reusing an `externalId` on another referral returns `409 external_id_conflict`. Build IDs that are unique across your pharmacy. For balance snapshots, where you'd naturally use a date, put the referral in the ID too.
- **What counts as the same content.** The incoming request is compared with the record **as it is now**, after small formatting differences are ignored:
  - money in any precision (`"40"` and `"40.00"`);
  - NDC hyphens and spaces;
  - `quantity` precision (`"30"` and `"30.000"`);
  - a missing field and `null`;
  - spaces around text values;
  - the same `asOf` instant written in different time zones.

  Anything else that differs is a conflict.
- **After a PATCH, the original create conflicts.** Once you've changed a record, resending its original `POST` returns `409`. Keep your own map from each `externalId` to the CaseXchange `id` it returned, and update existing records with `PATCH` instead of resending the create.
- **A voided fill still replays.** Voiding isn't part of a fill's content. Resending the create for a fill you've since voided returns `200` and the voided fill, with `voidedAt` set. It doesn't restore the fill or create a new one, so check `voidedAt`.
- **Replays work in any status.** The `externalId` is looked up before the referral status is checked and before linked IDs are validated. A replay therefore still returns `200` after the firm has closed or withdrawn the referral, or after it has been archived. Only a genuinely new record is refused with `referral_not_writable`. A replay still needs a key that can reach the case and referral, on a referral of a pharmacy.
- **Retries of the same request at the same moment** never create two records. One creates the record and the other gets the replay, or `409` if their contents differ.
- **Format.** 1–200 characters after spaces at either end are trimmed. An empty value returns `400 validation_error`. You can't change an `externalId` after creating the record.
- **Finding a record by `externalId`.** Use `GET .../pharmacy/fills?externalId=...` or `GET .../pharmacy/transactions?externalId=...`.

<Tip>
Always send an `externalId`. Without one, a request that timed out after CaseXchange saved it, followed by your retry, records the same fill or payment twice.
</Tip>

## Prescription and claim documents

Upload documents with `POST /med-cases/{caseId}/documents`, as described in [MedEx for medical providers](/api-reference/examples/medex-providers#integration-walkthrough). Two categories suit pharmacies:

| `category` | Use it for |
|---|---|
| `prescription` | A copy of a prescription |
| `claim_form` | A claim form: CMS-1500, HCFA or UB-04 |

The upload also takes three optional form fields, which work for every practice:

| Field | What it does |
|---|---|
| `externalId` | The same [idempotency](#idempotency) rules as the ledger. Here, "the same content" means the same case, `category`, `appointmentId`, `note` and replaced document, and the same file bytes, compared by SHA-256. A replay returns `200` with `"replayed": true` and doesn't store the file again |
| `supersedesDocumentId` | Marks an earlier document as replaced by this one. See below |
| `notify` | `"true"` (the default) or `"false"`. `"false"` skips the email notifications about the upload, and nothing else: the case history entry and the `document.uploaded` webhook still happen |

### Upload a claim form and link it to the fill

```bash
curl -X POST "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/documents" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -F "file=@claim-RX-100245.pdf" \
  -F "category=claim_form" \
  -F "externalId=prx-claim-100245-v1"
```

**Response `201 Created`:**

```json
{
  "data": {
    "id": "2c9f7e4b-6a13-4d8e-b5f2-1e0a9d8c7b36",
    "appointmentId": null,
    "fileName": "claim-RX-100245.pdf",
    "contentType": "application/pdf",
    "fileSize": 48213,
    "category": "claim_form",
    "source": "upload",
    "uploadedAt": "2026-10-02T14:12:00.000Z",
    "pending": false,
    "sharedWithProviders": true,
    "supersededAt": null,
    "supersededByDocumentId": null
  },
  "meta": { "requestId": "req_2a3b4c5d6e7f8a9b0c1d2e3f", "timestamp": "2026-10-02T14:12:00.000Z" }
}
```

The response doesn't include `externalId`. Keep the returned `id`, then set it on the fill as `claimDocumentId`, either when you create the fill or later with `PATCH .../pharmacy/fills/{fillId}`.

### Replace a document

To send a corrected claim form, upload it with `supersedesDocumentId` set to the one it replaces, and give it a new `externalId`:

```bash
curl -X POST "https://api.casexchange.com/api/public/v1/med-cases/5d0e8a3c-7b14-4c29-9f61-2a8e4b7c9d10/documents" \
  -H "X-API-Key: cxpp_std_your_key_here" \
  -F "file=@claim-RX-100245-corrected.pdf" \
  -F "category=claim_form" \
  -F "externalId=prx-claim-100245-v2" \
  -F "supersedesDocumentId=2c9f7e4b-6a13-4d8e-b5f2-1e0a9d8c7b36"
```

- The document you replace must be one **your organisation uploaded directly** to this case, and it must not already be replaced. Otherwise the upload returns `409 invalid_supersede`. If it was already replaced, `error.details.supersededByDocumentId` names the replacement; supersede that one instead.
- The original stays listed and downloadable. `GET /med-cases/{caseId}/documents` shows it with `supersededAt` and `supersededByDocumentId` set, and MedEx marks it as superseded.
- If the replacement is later deleted, the original becomes the current version again. A replay of the replacement upload after the **original** has been deleted returns `409 external_id_conflict`, because the replaced document is part of the upload's content.
- Repoint the fill with `PATCH .../pharmacy/fills/{fillId}` and `{ "claimDocumentId": "<the new id>" }`.

<Tip>
When you load a backlog of claim forms, send `notify=false` so the firm isn't emailed for every file. The uploads still appear in the case history.
</Tip>

## Errors

Errors use the standard envelope with `error.code`, `error.message` and, for these codes, `error.details`. See [Error Handling](/api-reference/error-handling) for the general rules and [MedEx for medical providers](/api-reference/examples/medex-providers#errors) for the authentication and rate-limit codes.

| Status | `error.code` | Meaning | What to do |
|---|---|---|---|
| `403` | `pharmacy_only` | The referral's practice isn't set up as a pharmacy (ledger writes), or yours isn't (`GET /med-cases/{caseId}/prescriptions`) | Ask CaseXchange support to check your setup. Ledger reads still work and return empty lists |
| `409` | `referral_not_writable` | The referral is `sent`, `under_review` or `rejected`, or archived. `error.details.status` and `error.details.isArchived` say which | Accept a `sent` or `under_review` referral first. A rejected or archived referral takes no new records. Replays still succeed |
| `409` | `fill_voided` | You tried to change or void a fill that's already voided | Leave it. If the fill is real, record a new fill with a new `externalId`, and reverse any payments posted to the voided one |
| `409` | `external_id_conflict` | The `externalId` is already used with different content. `error.details.existingId` is that record | Fetch `existingId` and compare. Fill: `PATCH` it. Transaction: `PATCH` `payer`, `reference`, `note` or `fillId`; if the money differs, reverse it and post a new transaction with a new `externalId`. Snapshot or document: use a new `externalId`. Rarely, an upload raced with one that was then deleted: this has no `details`; retry the upload |
| `400` | `immutable_field` | A transaction `PATCH` named `type`, `amount`, `transactionDate` or `reversesTransactionId`. `error.details.fields` lists them | Remove those fields. To change money, post a reversal |
| `400` | `invalid_reference` | A `prescriptionId`, `claimDocumentId`, `fillId` or `reversesTransactionId` isn't on this case or referral, the prescription isn't routed to you, or you can't see the document. `error.details.field` names it | Check the ID. Create fills before the transactions that name them |
| `409` | `invalid_supersede` | `supersedesDocumentId` isn't your organisation's own direct upload on this case, or it was already replaced (`error.details.supersededByDocumentId`) | Supersede the current version, or upload without `supersedesDocumentId` |
| `400` | `validation_error` | The body or query failed validation: a bad money string, a 10-digit NDC, a date not in `YYYY-MM-DD`, an unknown field, `reversesTransactionId` on a type other than `REVERSAL`, an empty `externalId`. `error.details.errors` lists each problem | Fix the request |
| `403` | `wrong_scope` | A firm key tried a ledger write or `GET /med-cases/{caseId}/prescriptions` | Use your pharmacy's provider key |
| `403` | `insufficient_tier` | A `read_only` key tried a write | Use a `standard` or `full` key |
| `403` | `restricted_access` | Your practice is restricted-access | Ask CaseXchange support |
| `404` | `not_found` | The case, referral, fill or transaction doesn't exist, isn't on that case or referral, or belongs to another practice | Check the IDs |

```json
{
  "error": {
    "code": "referral_not_writable",
    "message": "Pharmacy billing is not open while the referral is sent. Billing is open once the referral is accepted (and stays open through treatment, closure or withdrawal).",
    "details": { "status": "sent", "isArchived": false }
  },
  "meta": { "requestId": "req_3b4c5d6e7f8a9b0c1d2e3f4a", "timestamp": "2026-10-02T13:30:00.000Z" }
}
```
